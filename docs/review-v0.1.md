## Medium（Phase 1D 時点の指摘。上の表で対応状況を示す）

### M-1 参照整合性・ID 重複が検証されない（バックアップ復元）
- 箇所: `src/lib/validate.ts`（`localDataProblems`）、`src/lib/backup.ts`（`parseBackup`）
- 条件: 手編集・破損したバックアップ、または別ツールで作られた JSON を復元する。例: タスクが存在しない `projectId` を指す、作業時間が存在しない担当者を指す、同じ `id` のプロジェクトが2件。
- 実測: 孤立参照（task.projectId / assigneeAgentId、session.agentId / taskId）と重複 ID を含むバックアップが `parseBackup` で**受理される**ことを確認。
- 影響: 画面に「?」と表示される、集計が存在しないプロジェクト/担当者に紐付く、重複 ID の項目は編集・削除が両方に及ぶ。データ消失ではないが、UI と保存データの不一致が起きる。通常操作（アプリ内の編集）では発生しない（コード確認）。
- 修正案: `parseBackup` に参照・一意性の検査を追加（スキーマ変更なし）。保存済みデータに同じ検査をかける場合は、読み込み時は「警告」にとどめ、拒否は復元時のみにする（既存ユーザーのデータを突然読めなくしないため）。

### M-2 読み戻し不一致時の復旧が、他タブの直後の保存を上書きし得る
- 箇所: `src/lib/storage.ts`（`saveLocal` → `restoreAfterBadWrite`）
- 条件: タブ A の書き込みと読み戻しの数ミリ秒の間に、タブ B が同じキーへ保存した。A は不一致と判断し、保存前の値を書き戻す。
- 実測: 模擬ストレージでこの順序を再現し、B の保存が消えて A の保存前の値に戻ることを確認（`restored_previous` と報告される）。
- 影響: 他タブの保存内容の消失。窓は極めて狭く、実ブラウザでの発生は未確認（推測: まれ）。既知の「同時刻保存は保証できない」制約の延長にあるが、**復旧処理が能動的に上書きする**点が異なる。
- 修正案: 書き戻す前に現在値を読み、「自分が書いた値」または「読めない/空」の場合のみ書き戻す。それ以外（他タブの値）は触らず `conflict` として報告する。

### M-3 タスクを別プロジェクトに移すと、紐づく作業時間のプロジェクトが食い違う
- 箇所: `src/lib/domain.ts`（`updateTask`／`cleanTask`）
- 条件: 作業時間が記録されたタスクの「プロジェクト」を編集で変更する。
- 実測: 作業時間の `projectId` は旧プロジェクトのまま、タスクは新プロジェクトとなり、検証は通過することを確認。
- 影響: プロジェクト別合計は旧プロジェクトに計上される一方、タスクは新プロジェクトに表示される。作業時間の登録フォームは「タスクはそのプロジェクトに属する」ことを要求するため、規則の不整合になる。
- 修正案: 作業時間のあるタスクはプロジェクト変更を禁止する、または紐づく作業時間のタスク参照を外す（確認付き）。

### M-4 認証なしの公開 Function が、共有の GitHub 未認証レート制限を消費され得る
- 箇所: `netlify/functions/github-snapshot.ts`、`src/lib/github/handler.ts`
- 条件: 誰かが `/api/github-snapshot?repo=<許可リポジトリ>` を繰り返し呼ぶ（認証・呼び出し制限なし）。
- 影響: 1回の呼び出しで GitHub に4リクエスト。未認証の上限（60回/時間、Netlify の送信元 IP 単位と推測）に達すると、家主の同期が一時的に失敗する。Netlify の Function 呼び出し枠も消費される。漏れる情報は公開リポジトリの公開データのみ（許可リスト内）。許可リスト外のリポジトリは 403（実測）。
- 実測できていないこと: 実環境でのレート制限枯渇時の挙動（モックのみ）、送信元 IP が他の Netlify 利用者と共有されるか。
- 修正案: 応答にキャッシュ（例: `s-maxage`）を付けて呼び出しを集約する、`GITHUB_TOKEN` を設定して上限を上げる（設定時の動作は未検証）、Netlify 側のアクセス制限（サイトのパスワード保護など）を使う。いずれも実装・設定の追加が必要。

### M-5 リポジトリ変更後も手入力の Issue/PR 番号が残り、新リポジトリの別の項目として表示される
- 箇所: `src/lib/domain.ts`（`updateProject`、`linkInfo`）
- 条件: プロジェクトのリポジトリを `o/a` から `o/b` に変更する。
- 実測: タスクの `links`（例: Issue #1 / PR #2）がそのまま残ることを確認。新リポジトリを同期すると、同じ番号の別の PR の「マージ済み」等がカードに表示され得る（コード確認）。
- 影響: 承認判断の材料である GitHub 状態の誤表示（家主の承認状態は影響を受けない）。ユーザーガイドに注意を記載済み。
- 修正案: リポジトリ変更時に、影響を受けるタスクの紐付けを警告のうえ消去するか、紐付けにリポジトリ名を持たせる（後者はスキーマ変更になる）。
